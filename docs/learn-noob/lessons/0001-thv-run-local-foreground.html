ToolHive / Lesson 001约 20 分钟

从一个命令，追到容器部署

今天只回答一个问题：当用户执行 thv run --foreground IMAGE 时，ToolHive 如何从 CLI 走到真正的 workload 部署？

本课完成标准：合上页面后，你能凭记忆画出下面这条链，并说出每层为什么存在：CLI → RunConfig → Manager → Runner → Runtime → Deployer。

0. 先固定观察样本

我们选择前台模式，是为了让调用链保持在同一个进程里。暂时不展开后台模式、Registry、OAuth、middleware 细节和 Kubernetes。你可以把镜像名想象成一个已准备好的 MCP server 镜像：

thv run --foreground ghcr.io/example/my-mcp:latest

读代码技巧：不要从包名猜职责。先找到“用户动作的入口函数”，然后每遇到一次函数调用，只追进去一个层级，记录输入、输出和副作用。

1. 入口：main 只做进程级准备

01

打开 cmd/thv/main.go 的 main。它初始化日志、信号处理、启动前检查，然后调用：

cmd := app.NewRootCmd(...)
cmd.ExecuteContext(ctx)

这里的关键不是 Cobra 语法，而是 ctx：它把终止信号带给后面的调用链。入口层准备“运行环境”，不负责部署 MCP server。

2. CLI：把用户输入送到 runCmdFunc

02

在 commands.go，NewRootCmd 把 runCmd 挂到 root；在 run.go，runCmd 声明参数校验、PreRunE 和 RunE: runCmdFunc。

runCmdFunc 做两件事：取出第一个参数 serverOrImage，再把 -- 后的参数交给 MCP server，最后进入：

runSingleServer(ctx, &runFlags, serverOrImage, cmdArgs, ...)

此时 CLI 层还没有创建容器；它只完成“解析意图”。

3. runSingleServer：创建协作者，构造事实对象

03

runSingleServer 先通过 container.NewFactory().Create(ctx) 取得 runtime，再用 workloads.NewManagerFromRuntime(rt) 取得 workload manager。

然后调用 BuildRunnerConfig。这个函数把 flags、镜像、端口、transport、权限等信息收敛为一个 *runner.RunConfig。这就是本课第一个架构重点：

配置对象是层间契约。CLI 不把十几个零散参数一路传到 runtime，而是先构造一个可保存、可重放、可测试的运行描述。

接着保存 state，并因为我们指定了 --foreground，进入 runForeground → workloadManager.RunWorkload。

4. Manager：生命周期外壳，而不是 MCP 业务

04

打开 pkg/workloads/manager.go。DefaultManager.RunWorkload 先写入 starting 状态，再创建 runner.Runner，调用它的 Run。

如果容器是“异常退出且值得重启”，manager 处理重试、退避和状态更新；如果是其他错误，则标记 error 并返回。也就是说：

组件关心什么不关心什么
Manager状态、生命周期、重试、清理如何组装一个 HTTP transport
Runner一次运行的组装与启动CLI flag 如何解析

5. Runner：一次运行的组装中心

05

打开 pkg/runner/runner.go 的 Runner.Run。为了聚焦，本课只看三步：

  1. 根据 RunConfig 准备 transport 配置和 middleware 配置；
  2. 本地 workload 进入 runtime.Setup(...)；
  3. 用 setup 结果创建 transport 并启动它。

注意这里的设计：Runner 同时能处理 local 和 remote，但通过 if r.Config.RemoteURL == "" 分开。第一课只走 local 分支。

6. Runtime：把抽象配置翻译成部署动作

06

打开 pkg/runtime/setup.go。Setup 根据 transport 类型补充环境变量，例如 MCP_TRANSPORT 和 HTTP 端口，然后组装 DeployWorkloadOptions，最后调用抽象接口：

runtime.DeployWorkload(ctx, image, containerName, cmdArgs, ...)

到这里，“如何部署”被交给具体 runtime 实现。这个接口边界是第二个架构重点：上层只依赖能力，不依赖 Docker API 或 Kubernetes API 的细节。

7. 把整条 DFS 链复述出来

main
└─ app.NewRootCmd → cmd.ExecuteContext
└─ runCmd / runCmdFunc
└─ runSingleServer
├─ BuildRunnerConfig → *runner.RunConfig
├─ SaveState
└─ RunWorkload
└─ runner.Run
└─ runtime.Setup
└─ Deployer.DeployWorkload

一句面试版总结：

ToolHive 把 CLI 输入先收敛为 RunConfig，由 workload manager 管生命周期，由 runner 负责一次运行的组装，再通过 runtime/deployer 接口把配置翻译为具体容器部署，因此 CLI、运行编排和底层容器实现彼此解耦。

8. 回忆练习：先想，再看答案

不查代码，回答：为什么 RunWorkload 不直接把所有部署细节写进去，而要再创建一个 Runner？

因为 manager 管的是 workload 生命周期和状态，而 runner 管的是一次运行的组装；职责分离后，重试和清理逻辑不会和 transport、middleware、runtime 细节纠缠。

代码定位题：打开源码，找出从 RunConfig 到 DeployWorkload 之间传递的三个关键对象，并写下它们各自解决的问题。

RunConfig 描述运行事实；SetupResult 返回实际容器名和目标 URI；DeployWorkloadOptions 携带端口、stdio、权限和 Kubernetes patch 等部署选项。
