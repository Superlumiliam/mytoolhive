ToolHive / reference 001

thv run 的本地前台调用链

把一个 CLI 动作压缩成一条可复述的路径：命令入口接收参数，构造 RunConfig，manager 负责生命周期，runner 负责一次运行，runtime 负责把配置变成容器。

main → NewRootCmd → runCmd → runCmdFunc → runSingleServer
→ BuildRunnerConfig → SaveState → RunWorkload
→ Runner.Run → runtime.Setup → Deployer.DeployWorkload

每层只记一个问题

层代码位置它回答的问题
CLIcmd/thv/app/run.go用户输入了什么？应该走哪条分支？
配置cmd/thv/app/run_flags.goflags 如何变成稳定、可传递的 RunConfig？
Workload managerpkg/workloads/manager.go生命周期和状态如何管理？是否需要重试？
Runnerpkg/runner/runner.go一次 MCP server 运行如何组装 middleware、transport 和 runtime？
Runtimepkg/runtime/setup.go如何把抽象配置转换为容器部署参数？
具体实现pkg/container/runtime/Docker、Kubernetes 等实际 deployer 如何执行？

三个 Go 观察点

  • workloads.Manager 是调用者依赖的接口；CLI 不需要知道具体 manager 结构。
  • RunConfig 是跨层传递的“事实对象”，减少函数参数爆炸。
  • context.Context 从 CLI 进入底层，承载取消和超时边界。
