第 9 课：状态不是一份文件

校准日期：2026-07-17 · 预计 25 分钟 · 唯一目标：面对“状态显示 Running 但不可用”或清理失败，你能区分期望配置、supervisor 进程、ToolHive status、runtime workload 与 proxy 健康，并按证据校准状态。

任务钩子

status JSON 写着 Running、process_id 也非零，但容器已经退出；或者容器仍在、supervisor 已死。哪个才是真相？答案不是挑一份“权威状态”，而是理解每层回答不同问题，并知道读取路径如何合并与修正。

RunConfig

想运行什么；restart/update 的输入，不证明当前存在。

Status JSON

ToolHive 观察到的阶段、context、timestamps、process_id。

Supervisor

detached proxy/Runner 进程；PID 只是一条定位线索。

Runtime

container/pod 的实际状态；remote workload 没有本地 container。

本地 detached 生命周期

Save RunConfig → spawn commit: Starting → re-exec foreground child → Set process_id → Runner deploy/proxy/readiness → Running ├─ expected stop: Stopping → Stopped, PID reset ├─ delete: Removing → container → supervisor → state/status cleanup ├─ unexpected container exit │ → restart sentinel → Starting + backoff → Running | Error └─ auth recovery: AuthRetrying (仍作为自恢复 workload 展示)
状态校准：本地 fileStatusManager 读取 status file 后，若是 Running 会再验证 runtime/PID/proxy；文件缺失时会回退到 runtime discovery。Kubernetes 使用 runtimeStatusManager，SetStatus/PID 多数是 no-op，观察源天然不同。

五层证据矩阵

证据能证明不能证明
RunConfig持久运行意图与 restart 输入container、proxy、PID 仍存在
status + context最近一次 ToolHive transition没有并发/崩溃造成陈旧

PID 不是进程身份：当前 tracked-PID stop 路径会直接使用 status 中的正 PID，不调用 ToolHive/workload 身份校验；Running 校准也主要检查该 PID 是否存在。陈旧或复用的 PID 可能导致误判，stop/delete 甚至可能终止无关进程。只有按端口发现进程的兜底路径会额外验证身份，所以操作前应联合命令行、端口、日志和 runtime 证据。

Stop 与 Delete 不同：stop 保留 RunConfig/status 以便 restart；delete 要移除 container、停止 supervisor 并清理 client/state/status。container 删除在 supervisor 停止之前，代码说明这样做是为了防止 supervisor 重新创建；任何中途错误都可能留下部分资源。

走读 7 个锚点

  1. pkg/workloads/manager.go：RunWorkload、Detached、tracked-PID stop、delete/restart/update 与 retry。
  2. pkg/workloads/statuses/status.go：file 与 runtime status manager 的部署模式分流。
  3. pkg/workloads/statuses/file_status.go：非对称的 file/runtime/PID/proxy 合并和陈旧状态修正。
  4. pkg/workloads/statuses/pid.go：旧独立 PID 文件迁移。
  5. pkg/process/toolhive_proxy.go：按端口兜底发现时的 ToolHive/workload 身份验证。
  6. pkg/runner/runner.go：何时写 Running、返回 restart sentinel 与 health/auth transitions。
  7. pkg/workloads/types/types.go：runtime ContainerInfo 如何变成用户看到的 Workload。

先预测，再展开

spawn 成功后 shell 返回，status 一定已经 Running 吗？

不一定。父进程只记录 child PID；child 还要加载配置、解析秘密、deploy、启动 transport。期间合理状态是 Starting，失败会在 child 日志/status 中出现。

container 意外退出由 Transport 自己无限重启吗？

不是 Transport 自己重启。只有 restart-needed sentinel 进入 DefaultManager 的退避循环；单轮默认最多 10 次，稳定运行 30 秒会重置计数与延迟，因此长期总次数仍可能无限。其他错误直接进入 Error。

独立 PID 文件还是当前主存储吗？

不是。当前 process_id 在 status JSON；独立 PID 文件主要用于迁移。conditional reset 还避免旧进程退出时清掉新 replacement 的 PID，但不等于验证 PID 身份。

测试取证

  • pkg/workloads/manager_test.go：foreground retry、detached commit/PID、stop/delete/restart/update 的成功与部分失败。
  • pkg/workloads/statuses/file_status_test.go：file/runtime merge、PID migration、proxy down、corrupt JSON 与并发锁。
  • pkg/workloads/statuses/pid_test.go：migration 与 PID file semantics。
  • 待补覆盖：tracked PID 复用不得误杀、remote proxy 健康、可取消 backoff，以及 update 回滚/原子性。

选择最直接的层；三个选项均为 6 个字符。

A. restart 报找不到保存配置。

B. container running，但 proxy port 无监听。

C. supervisor 存活，container 已 exited。

5 分钟实作：写一份状态对账

为一个“Running 但连接失败”写六行：① RunConfig 是否存在；② status/context/PID；③ PID 身份；④ runtime workload；⑤ proxy health/log；⑥ 应修正到哪个状态或进入哪个清理动作。把答案发给教师获得反馈；展示出理解后才写学习记录。
