第 2 课：部署形态改变的是控制权与信任边界

校准日期：2026-07-17 · 预计 25 分钟 · 唯一目标：面对一个运行场景，你能指出“谁提交意图、谁持有执行权限、状态以谁为准、谁修复漂移”，并据此选择本地 CLI、本地 API 或 Kubernetes Operator。

任务钩子

安全同事问：“同一个 MCP server，用 thv run、ToolHive Studio，或 MCPServer CR 部署，有什么本质区别？”如果只回答“一个在电脑上、一个在集群里”，就漏掉了治理问题：控制请求跨过了哪些身份边界，哪个进程或控制器有权改变实际状态，故障后又由谁恢复？

先打开 部署形态与信任边界速查。以后分析任何部署形态，都先问四个问题：

1 · 意图入口
谁发出“创建、更新、停止”的请求？是本地 shell、HTTP 调用者，还是 Kubernetes API 中的 CR？
2 · 权限持有者
谁能调用容器 runtime 或 Kubernetes API？这个身份的权限是否超出它管理一个 workload 所需的范围？
3 · 状态事实源
重启后用什么重建判断？本地 RunConfig/PID/status 文件，还是 Kubernetes API 中的 spec、status 与子资源？
4 · 漂移修复者
这是一次命令触发的生命周期，还是 controller 会持续比较期望与实际并再次收敛？

三种形态，一条共同执行主线

本地 CLI

入口：本地 OS 用户执行命令。

执行：workload manager 重启当前 thv 为 detached supervisor，再调用本地容器 runtime。

状态：本机 XDG 目录中的 RunConfig、PID、status 与日志。

本地 API

入口：thv serve 暴露 HTTP/Unix socket 控制面；默认绑定 127.0.0.1，可配置 OIDC。

执行：API handler 仍调用同一个 workload manager 和 detached supervisor 模型。

状态：仍以本机状态文件为主；API 是访问边界，不是新的持久化事实源。

Kubernetes Operator

入口：调用者向 Kubernetes API 提交 MCPServer spec。

执行：Operator 创建 Proxy Deployment、Service 和 RunConfig ConfigMap；Proxy Runner 再管理 server StatefulSet。

状态：期望和观察状态通过 Kubernetes API 持久化，controller 持续 reconcile。

本地 CLI: shell → thv run → RunConfig → detached thv → Proxy → container runtime 本地 API: caller → thv serve → WorkloadService ───────────────┘ Kubernetes: caller → K8s API → Operator → Proxy Deployment → StatefulSet
关键纠正：thv serve 增加了一个可被程序调用的控制入口，却没有把所有 workload 收进 API server 进程。CreateWorkloadFromRequest 保存 RunConfig 后仍调用 RunWorkloadDetached；因此 API server 退出，不等于所有 detached Proxy 都随之退出。相反，Operator 模式把“持续修复实际状态”交给 reconciliation。

像带新同事一样走读 7 个锚点

  1. cmd/thv/app/run.go：定位 runCmdFunc / runSingleServer，找到 RunConfig 保存与 RunWorkloadDetached 的交接点。
  2. pkg/workloads/manager.go：读 RunWorkloadDetached 和 spawnDetached；用一句话解释为什么不能用 exec.CommandContext 绑定父请求。
  3. cmd/thv/app/server.go：找到默认监听地址、Unix socket 与 OIDC 配置；列出把 API 从 loopback 暴露到网络后新增的两项审查。
  4. pkg/api/v1/workload_service.go：沿 CreateWorkloadFromRequest 标出 policy gate、SaveState 与 detached start 的顺序。
  5. cmd/thv-operator/controllers/mcpserver_controller.go：在 Reconcile 中只定位 RunConfig ConfigMap、Deployment、Service 和 status；不要下钻所有配置分支。
  6. cmd/thv-operator/controllers/mcpserver_controller.go：读 SetupWithManager，确认哪些资源变化能重新排队，而不只看一次 Reconcile。
  7. cmd/thv-proxyrunner/app/run.go：观察 Kubernetes runtime 如何进入 runner.NewRunner(...).Run(ctx)，连接 Proxy Deployment 与 server StatefulSet 两个执行单元。

最后用相邻测试确认契约，而不是把注释当事实：API 看 pkg/api/v1/workloads_test.go，Operator 看 mcpserver_runconfig_test.go 与 mcpserver_rbac_test.go，Proxy Runner 看 cmd/thv-proxyrunner/app/run_test.go。

立即检索

先在脑中作答，再展开反馈。

1. API server 退出后，已经启动的本地 workload 必然一起退出吗？

不必然。API 创建路径调用 RunWorkloadDetached，子进程被设计为脱离触发它的请求和父进程继续运行。应分别检查 API 控制入口与 workload supervisor。

2. 把 thv serve 从 loopback 改为对外监听，只增加了网络连通性吗？

不是。它把创建、更新、停止 workload 的高影响控制操作带到新的身份边界，必须同时审查认证、授权、TLS/网络暴露和 API 进程持有的本地 runtime 权限。

3. Operator 与“定时执行一遍部署脚本”的关键差别是什么？

Operator 通过 watch 与 reconcile 持续比较期望状态和实际状态，并把结果写回 status；一次性脚本完成命令后不会天然承担持续漂移修复。
