第 16 课：一次调用需要四种证据

校准日期：2026-07-18 · 预计 30 分钟 · 唯一目标：面对一次 tools/call 事件，你能为“发生多少、慢在哪里、谁做了什么、进程为何失败”分别选择正确证据，并指出每种证据的采样、聚合、覆盖和隐私盲区。

任务钩子

Dashboard 上 error rate 为零，不等于工具没有返回 JSON-RPC error；一条 trace 找到慢点，也不等于所有调用都有完整取证记录。企业治理需要把观测问题先翻译成证据类型，再谈 collector、查询和告警。

Client HTTP traceparent / MCP params._meta.traceparent (_meta takes precedence) │ ▼ MCP parser → telemetry middleware → authz → audit middleware → backend handler │ │ ├─ sampled server span └─ structured audit event ├─ counters/histograms audit_id + subject + target + outcome │ └─ transparent proxy / vMCP client injects W3C headers │ ▼ backend client span Process logs explain runtime decisions; health/CR Conditions describe observed state. Neither is automatically a per-call proof.
证据四问：先问需要的是 fleet 趋势、单次因果链、逐事件责任记录，还是进程诊断上下文；再检查这条证据是否被采样、是否只看 HTTP、是否覆盖了该 middleware、以及是否包含敏感数据。

四种信号回答四类问题

信号最擅长回答不能单独证明
Metrics请求量、延迟分布、HTTP error rate、活连接和 vMCP backend 趋势某个用户的完整事件；label 是聚合维度，不是逐调用记录
Traces被采样调用的父子关系、每一跳耗时与 span error未采样请求、身份或审计合规；100% sampling 也不提供不可篡改保证
Audit启用、未过滤且成功写出时，记录到达 middleware 的事件、主体、来源、target、outcome 和 audit_id后端副作用必然发生、日志不可删改或 collector 健康；audit_id 也不是内建 trace_id join key
Process logs配置解析、启动、连接、exporter 和 reconcile 的诊断上下文；当前是独立 slog 管道稳定 schema、逐事件完整性或 fleet 级数值趋势；当前没有 OTLP logs provider

Status 不是第五种请求遥测：Pod readiness、CR Phase 和 Conditions 说明控制器观察到什么，不说明一次 tools/call 是否完成；反过来，一条成功 span 也不能证明所有副本 Ready。部分 /health 与 /metrics 路径明确绕过业务 middleware。

MCPTelemetryConfig 是 MCPServer、MCPRemoteProxy、VirtualMCPServer 的同 namespace 共享配置；openTelemetry.enabled 先控制 OTLP 映射，每个 consumer 可覆盖 serviceName。配置 hash 触发 reconcile/rollout，不是进程内热加载。MCPServer/RemoteProxy 的旧 inline telemetry 已 deprecated；当前 Operator vMCP converter 只从 TelemetryConfigRef 填充 telemetry，不能按旧文档假定 inline 仍生效。

两个端到端核对点：CA bundle 会通过 ConfigMap mount；但 sensitiveHeaders 当前只可确认被转成 TOOLHIVE_OTEL_HEADER_* Secret env，仓库中尚未找到 runtime 将它们合并进 telemetry.Config.Headers 的生产路径。serviceName 的注释还写默认 thv-<server>，Operator converter 实际传入未加前缀的 workload name。两处都应以运行测试验证并可作为贡献点。

Valid=True 只证明 spec：MCPTelemetryConfig controller 校验字段并计算 hash，不主动探测 collector 可达性。错误 CA/PEM 可能阻止启动；运行期 collector 宕机通常只造成遥测失明，业务仍可能 Ready。还要用 exporter 日志、collector self-metrics 和端到端样本验证交付。

传播链也有边界

  • 入口先从 HTTP headers 提取 W3C context，再从已解析 MCP params._meta 提取；后者按 MCP 约定优先。
  • transparent HTTP proxy 与 vMCP backend client 会向出站 HTTP 注入 traceparent/tracestate；backend 仍必须自行启用兼容 instrumentation 才会产生自己的 span。
  • InjectMetaTraceContext helper 存在，但当前生产路径未调用；不能推断所有出站 MCP _meta 都被改写。SSE /sse 还有独立连接统计分支。
  • traceparent 是关联载体，不是 span、认证凭据或审计记录；provider/middleware 才负责创建、采样和导出 span。

遥测本身是数据出口：tool/resource ID 可能形成高基数 labels；span 可包含经启发式敏感词过滤和截断后的 tool arguments，以及显式选择的 environment variables。过滤不是字段级安全证明，配置前仍要做秘密与 PII 评审。

HTTP 200 可能是两种结果

telemetry middleware 当前按 HTTP status 分类：2xx span 为 Ok，metric status 为 success。MCP 常把 JSON-RPC error 放在 HTTP 200 body 中，因此 telemetry 可能把 application failure 计为 success；vMCP backend telemetry 也主要依据 Go error，IsError=true 结果不一定成为 error span。Audit 默认检查最多 512-byte response prefix，即使不记录 response data，也可把这类结果标成 application_error 并记录 error code/message。

Audit 本身默认关闭；Operator 的 spec.audit.enabled: true 使用默认配置：request/response body 不落日志、application error detection 开启、输出 stdout。若启用 payload，仍受 size limit，但必须额外做 secret/PII 风险评审；默认输出也没有内建签名或 WORM 保证。

5 分钟实作：调用证据账本

选一条真实 tools/call，写八行：① service.name；② incoming trace carrier；③ sampling rate；④ server/backend span；⑤ counter/histogram；⑥ audit subject/target/outcome；⑦ HTTP 200 JSON-RPC error 如何识别；⑧ collector 不可达时用什么证明。把账本发给教师获得反馈；展示出理解后才写学习记录。
