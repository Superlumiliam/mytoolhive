第 4 课：RunConfig 是控制面契约

校准日期：2026-07-17 · 预计 25 分钟 · 唯一目标：面对一个 RunConfig 字段或导入导出变更，你能把它归入“持久契约、运行注入、秘密解析”之一，并判断它在哪一层被默认、校验、保存或丢失。

任务钩子

同事把本地 RunConfig 导出为 JSON，手工加入 Deployer 和 API key，然后期待导入另一台机器后原样运行；又把它导出为 Kubernetes manifest，期待所有治理设置都保留。这里有三个错误假设：运行时对象会被序列化、秘密值应该随配置迁移、Kubernetes 转换是无损往返。

01

持久契约

身份、镜像、参数、transport、port、permission profile、中间件配置与秘密引用等声明式意图，可写入 JSON 并在进程间交接。

02

运行注入

Deployer、build context、端口复用状态等依赖当前进程或构建过程，不属于 wire format，读取后必须重新注入。

03

秘密解析

受管理秘密应以引用持久化，实际值在 Runner 或 Kubernetes pod 边界解析；这是生命周期约定，不是通用 JSON 自动脱敏。

核心判断：RunConfig 是控制面共享的 wire contract，但不是“正在运行进程的内存快照”。完整的执行需要：持久意图 + 本地 runtime 注入 + 环境中的秘密与外部资源。

同一契约，三种进入方式

CLI flags / registry API request │ │ └──────── builder + defaults + validation ────────┐ ▼ RunConfig intent │ WriteJSON / SaveState ─────────────────┤ ▼ ReadJSON → inject Deployer → resolve secrets → Runner MCPServer CR → operator builder + operator validation → ConfigMap/runconfig.json │ ▼ proxy-runner ReadJSON → inject Kubernetes runtime → Runner

不要把 decode 当 validation：ReadJSON 会补齐部分 nil map/slice、为缺失的 schema_version 填当前值、迁移两类旧秘密字段并规范化 ProxyMode；它目前不拒绝未知或未来 schema，也不做通用必填字段校验。CLI/API builder 与 Operator 的额外校验才是不同入口的主要约束层。

契约分层表

类别代表值保存与恢复语义
身份与来源Name、image/remote URL、registry provenance进入 JSON；用于恢复“想运行什么”。
执行与流量args、env、volumes、transport、host、ports、ProxyMode进入 JSON；builder 负责大量默认值和组合校验。
治理与安全permission profile、network isolation、middleware、secret references配置或引用进入 JSON；实际权限和秘密仍需运行环境兑现。
编排与版本SchemaVersion、generation、scaling、K8s pod patch进入 JSON；当前 schema 字段是标记/默认值，不是兼容性闸门。
运行时对象Deployer、build context、existing port不属于 JSON；import、detached child、proxy-runner 都要按环境重建或注入。
解析后秘密secret store 取出的 API key、OAuth client secret、bearer token受管理路径应只在内存或 pod 环境中出现，不应写回状态文件。

按职责走读 8 个锚点

  1. pkg/runner/config.go：先读 struct tags，再读 WriteJSON / ReadJSON；确认“写什么、读时修什么、没有校验什么”。
  2. pkg/runner/config_builder.go：比较 NewRunConfigBuilder 与 NewOperatorRunConfigBuilder，追踪 options、defaults、env 与 validateConfig。
  3. pkg/state/runconfig.go：确认 SaveRunConfig / LoadRunConfig 只是存储与 codec 边界。
  4. cmd/thv/app/run.go：在 runFromConfigFile 找到 ReadJSON、runtime 注入、policy check、SaveState 与执行顺序。
  5. cmd/thv/app/export.go：比较 JSON export 与 --format k8s 的不同保证。
  6. pkg/export/k8s.go：逐字段确认 RunConfig → MCPServer 的转换与缺口。
  7. cmd/thv-operator/controllers/mcpserver_runconfig.go：确认 CR 如何经 operator builder、额外校验与 ConfigMap 交给 proxy-runner。
  8. cmd/thv-proxyrunner/app/run.go：确认集群进程如何读取同一 JSON，再注入 generation、image、runtime 和 pod patch。

四个容易写错的断言

“有 schema_version，所以导入会拒绝不兼容版本。”

不成立。当前 ReadJSON 对缺失值补 v0.1.0，但没有版本范围/equality 检查或通用 migration dispatcher；测试 fixture 甚至能读取 v1。新增兼容性门需要明确迁移策略和回归测试。

“RunConfig 不可能持久化明文秘密。”

过强。受管理的 secret-reference 路径遵循“先保存引用、后解析值”，但 EnvVars、plaintext header 和部分兼容字段本身可序列化。安全评审必须检查具体字段与生命周期，而不是依赖 struct 名称。

“JSON import 会重新走 builder 的所有校验。”

不成立。runFromConfigFile 直接 ReadJSON 后注入 runtime；它不会重新调用 RunConfig builder。入口间的校验强度并不完全相同。

“export --format k8s 是可逆格式转换。”

不成立。它把 RunConfig 转成 MCPServer，并明确警告 secrets、telemetry、OIDC 需要额外资源；permission、audit、authz 等也可能降级或只做部分映射。

测试如何证明边界

  • pkg/runner/config_test.go：JSON round-trip、默认/迁移行为，以及允许 schema_version: "v1" 的当前事实。
  • pkg/runner/config_builder_test.go：CLI/Operator builder、permission、volume、env、transport、registry 与 middleware 组合。
  • pkg/export/k8s_test.go：哪些字段能映射到 MCPServer、remote URL 等哪些输入会失败。
  • cmd/thv-operator/controllers/mcpserver_runconfig_test.go：CR → RunConfig ConfigMap 的 operator 契约。
  • cmd/thv-proxyrunner/app/run_test.go：proxy-runner 读取后对 generation 等运行信息的覆盖。

3 分钟字段分诊

选择字段真正所属的层。三个选项均为 6 个字符，避免长度泄题。

A. Transport 与 ProxyPort。

B. Deployer runtime 对象。

C. secret store 返回的 API key 实际值。

5 分钟实作：评审一个新字段

假设要新增 RetryBudget。写六行：① 它是持久意图还是运行状态；② CLI/API/Operator 哪些入口设置它；③ 默认值在哪一层产生；④ ReadJSON 是否需要迁移；⑤ JSON 与 K8s export 是否都能保真；⑥ 哪三个邻近测试锁定契约。把答案发给教师，我会按“分类、入口一致性、兼容性、秘密/运行边界、测试证据”反馈；展示出理解后才写入学习记录。

一手资料

主读：RunConfig contract 与 RunConfig builder。配套事实源：state persistence、CLI export、Kubernetes conversion 与 Operator rendering。架构文档提供设计背景；涉及 schema 校验、秘密和 import/export 时，以当前源码与测试为准。
