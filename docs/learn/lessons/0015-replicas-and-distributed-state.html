第 15 课：副本数不是可用性承诺

校准日期：2026-07-18 · 预计 30 分钟 · 唯一目标：给定一次扩容或 Pod 故障，你能逐项说明请求会落到哪里、哪些会话数据可恢复、哪些活状态必然丢失，并据此判断真正的可用性边界。

任务钩子

把 replicas: 3、sessionAffinity: ClientIP 和 Redis 同时打开，看起来像“高可用”。但它们分别只改变计算容量、Service 路由和可恢复元数据；若把三者当成一个保证，最危险的故障会在扩容成功后才出现。

Client request │ ▼ Kubernetes Service ── sessionAffinity ──► proxy / vMCP Pod │ │ │ replicas changes compute copies ├─ node-local live connections + LRU │ │ │ └─ Redis: restorable session metadata ▼ │ cache miss / Pod replacement Backend StatefulSet / remote backend ◄──── RestoreSession reconnects │ └─ browser context, transaction, open file and in-flight call stay backend-local
四问审计法：① 扩的是哪种 Pod？② 下一次请求落到哪一副本？③ 新副本能从存储重建什么？④ 已经打开的连接和后端副作用由谁恢复？只有四问都有答案，才可以讨论“高可用”。

三个旋钮，三个不同承诺

旋钮能做什么不能保证什么
spec.replicas控制 MCPServer proxy、vMCP aggregator 或 RemoteProxy Deployment 的期望副本；为 nil 时不写 Deployment replicas，让 HPA/KEDA 等控制不共享状态、不保证每个副本 Ready，也不自动扩大 backend
sessionAffinityClientIP 让 Service 尽量把同源连接粘到同一 proxy Pod；None 允许分散不持久化 session；Pod 消失即失效，NAT/负载均衡器还可能让大量用户共享同一源 IP
sessionStorage: redis跨 Pod 保存带 TTL 的 session 记录；vMCP 可恢复 identity binding、backend ID/backend session ID，再重连后端重建工具视图与路由不保存活 TCP/SSE 连接、进程内 MultiSession/路由表、backend 浏览器/事务/文件状态或正在执行的 tool call 结果

Redis 不是复制运行时：Pod 死亡时 in-flight 调用仍会无响应；恢复连接也不等于恢复 backend 内部状态。会修改外部世界的工具需要调用方重试策略与幂等保护。

MCPServer 有两种副本

字段当前实现对象必须核对的限制
replicasproxy runner Deploymentstdio transport 会把大于 1 的 proxy 副本压回 1；scale-to-zero 仍允许。即使 HPA 从 nil 扩大，也会被后续 reconcile 纠正
backendReplicasRunConfig 经 proxyrunner/Kubernetes runtime 创建的 backend StatefulSetAPI 注释仍称“backend Deployment”，与实现漂移；stdio attach 选择首个 Pod，设置多个 backend 不能直接推导为吞吐扩容

VirtualMCPServer 和 MCPRemoteProxy 只有一组 proxy/aggregator replicas；它们没有 backendReplicas，因为后端是被发现或远端引用的独立 workload。

恢复的是记录，不是时间

vMCP Pod-local LRU

每 Pod 默认缓存 1,000 个 MultiSession。淘汰会关闭该对象持有的 backend 连接；若 Redis 记录仍在，下一次访问可触发 RestoreSession 重建连接。

TTL 的两套时钟

vMCP session metadata 默认 TTL 为 30 分钟；MCPServer proxy transport session 默认 2 小时。Redis 的 Load 使用 GETEX 滑动续期，因此持续活跃可不断延长，但空闲满一个 TTL 后无法再恢复。

Redis 自己故障

Redis 在 session 请求热路径上。没有可用记录时，另一 Pod 无法重建 session；Redis 重启若丢失数据，客户端必须重新 initialize。是否启用持久化是部署者的可用性取舍，不是 ToolHive 自动保证。

Status 是观测信号，不是证明

  • readyReplicas 是已观察到的 proxy/vMCP Pod 数，不代表 backend session、Redis 或每次 tool call 都健康。
  • 当前 controller 的 Ready/Running 判定可在“至少一个” proxy/vMCP Pod 可用时成立；不能把 Phase=Running 读成“所有 desired replicas 已就绪”。RemoteProxy 的统计还可能只基于 Pod Running。
  • SessionStorageWarning 是 advisory condition，不阻止创建；它只看显式 spec.replicas > 1 与 CR 中的 sessionStorage。nil replicas 被 HPA 扩大时不会触发，环境默认 Redis 地址生效时又可能仍误报。

运维判据：同时观察 desired/updated/ready replicas、session restore 错误、Redis 延迟/容量、backend 连接失败和业务级调用成功率。单个 Condition 只回答它实际测量的问题。

走读 8 个锚点

  1. api/v1beta1/{mcpserver,virtualmcpserver,mcpremoteproxy}_types.go：三类 replicas、affinity 与 storage API。
  2. controllers/mcpserver_controller.go：nil passthrough、stdio cap 与 warning 判定。
  3. controllers/mcpserver_replicas_test.go：HPA hands-off、cap、condition 和 readyReplicas 的可执行规格。
  4. controllers/mcpserver_runconfig.go：backendReplicas/Redis 进入 RunConfig。
  5. pkg/container/kubernetes/client.go：backend StatefulSet 与副本收敛。
  6. pkg/vmcp/server/sessionmanager/{factory,session_manager}.go：Pod-local LRU、cache miss 与 metadata load。
  7. pkg/vmcp/session/factory.go：恢复线索写入、backend 重连与 RouteTable 重建。
  8. pkg/transport/session/storage_redis.go 与 docs/arch/13-vmcp-scalability.md：GETEX TTL、容量和故障约束。

3 分钟机制分诊

三个选项均为 6 个字符。

A. HPA 把 vMCP Deployment 从 1 扩到 3。

B. Service 对同一来源启用 ClientIP affinity。

C. 原 vMCP Pod 消失，另一 Pod 从 Redis RestoreSession。

5 分钟实作：故障承诺表

任选一个生产配置，写六行：① proxy desired/ready；② backend desired/ready；③ Service affinity；④ session store 与 TTL；⑤ Pod 死亡后可重建的数据；⑥ 必然丢失的连接/后端状态/in-flight 副作用。再分别模拟“proxy Pod 被驱逐”和“Redis 数据丢失”。把表发给教师获得反馈；展示出理解后才写学习记录。
