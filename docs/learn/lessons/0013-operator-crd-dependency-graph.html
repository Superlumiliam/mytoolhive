第 13 课：引用本身不会触发 Reconcile

校准日期：2026-07-17 · 预计 30 分钟 · 唯一目标：给定一条 CR 引用边，你能判断源对象变化是否会通过 owner watch、显式 mapper、runtime watch 或根本不触发传播，并写出最终 condition、hash/checksum 与 rollout 的证据链。

任务钩子

更新 MCPOIDCConfig 后，为什么引用它的 MCPServer 会滚动，而只在 YAML 中写了一个任意对象名却不会？Kubernetes API 不理解业务引用；只有 controller 注册了 watch/index/mapper，并在 reconcile 中消费引用，边才真正“通电”。

MCPTelemetryConfig.spec changes ├─ its controller validates → status.configHash / Valid / referencingWorkloads └─ VirtualMCPServer explicit watch + mapper → consumer reconcile ├─ read producer spec → TelemetryConfigRefValidated / telemetryConfigHash (evidence) └─ render {vmcp}-vmcp-config ConfigMap → content-checksum annotation → Deployment PodTemplate runconfig-checksum → Kubernetes Deployment controller rolls Pods
读图规则：箭头必须标注机制。spec.fooRef 只是数据；Watches + EnqueueRequestsFromMapFunc 才把被引用对象事件映射回 consumer；Owns 则利用 child 的 controller owner reference 自动映射回 owner。

四种传播机制

机制适用关系能保证 / 不能保证
Forcontroller 的主 CR主资源 create/update/delete 等事件入队；具体过滤由 predicates 决定，不覆盖任意 peer ref
Owns + ownerRef某 workload controller 创建的 Deployment/Service/ConfigMap 等child 事件映射 owner、删除时 GC；不表达共享配置引用
显式 Watches + mapperOIDC/Authz/Telemetry/Group/ToolConfig 等 peer只 enqueue mapper 返回的 consumer；mapper 的 namespace、字段、predicate 是边界
Pod 内 runtime watchdiscovered vMCP DynamicRegistry无需 Operator rollout 即可更新运行时 registry；不自动改 CR spec 或旧 session 快照

Field index 不是第五种触发器：它只加速 MatchingFields 反查。Telemetry consumer mapper 当前仍是同 namespace 全量 List 后按 ref 过滤；index 由 MCPTelemetryConfig controller 用来维护 referencingWorkloads 和 finalizer 删除保护。

Owner reference 不能替代引用图：共享 MCPOIDCConfig 不应由某个 MCPServer 所有，否则删除一个 consumer 可能级联删除所有人共享的配置。反向 watch 与 reference status/finalizer 才适合多 consumer 关系。

还要审计“不连通边”：MCPServer 与 MCPRemoteProxy 会校验 groupRef，但它们的 controller 不 watch MCPGroup；MCPServer 也不 watch Secret/普通 ConfigMap，MCPRegistry 不 watch pgpass Secret，vMCP 只为 inline authz ConfigMap 注册 Data/BinaryData watch。被引用对象变化可能必须通过 consumer spec 变化、引用 CR 变化、runtime watch 或 Pod 重启传播。

从事件到 rollout 的六步证据

  1. 确认变更对象的 namespace/name 与 consumer ref 完全匹配。
  2. 在 consumer 的 SetupWithManager 找对应 Watches 与 mapper。
  3. 检查 predicate 是否过滤了这类变化；例如 authz ConfigMap 只关心 Data/BinaryData。
  4. 在 Reconcile 中验证引用并写 Valid/NotFound/Invalid condition 与 config hash。
  5. 确认渲染后的 RunConfig/vMCP ConfigMap 内容或 checksum 发生变化。
  6. 确认 checksum 进入 Deployment Pod template annotation，触发 rollout；仅 status hash 改变不必然重启 Pod。

Finalizer 与 ownerRef 回答不同问题

MCPServer 为什么还要 finalizer？

它的一级 Deployment/Service 有 ownerRef，但 proxy-runner 创建的 backend StatefulSet/headless Service 等并非 controller 直接 owned watch 的全部对象；finalizer 在 CR 消失前执行显式清理。MCPRemoteProxy 则只 owns Deployment/Service，没有同样 finalizer。

VirtualMCPServer 为什么没有 finalizer？

其 Operator 管理的 Deployment、Service、ConfigMap、RBAC/HMAC Secret 都设置 owner reference，依赖 Kubernetes cascade GC。删除策略不能从“都是 Operator CR”类推，必须看资源所有权。

共享 config 的 finalizer 做什么？

反向引用覆盖并不统一：OIDC/Authz/Telemetry 跟踪 MCPServer、MCPRemoteProxy、VirtualMCPServer；ExternalAuth 不含 vMCP/MCPServerEntry，ToolConfig 删除保护只跟踪 MCPServer。finalizer 只能保护它实际索引到的 consumer，不是全图引用完整性保证。

状态不是触发器

ObservedGeneration 说明 controller 看过哪个 spec generation；condition 给出结果与 reason。三种摘要不能画成数据管道：① producer status.configHash 是共享 CR spec 摘要；② ConfigMap content-checksum 是最终渲染内容摘要；③ PodTemplate runconfig-checksum 是 rollout 标记。真正入队的是 watch/requeue，真正滚动的是 Deployment template 变化；status hash 只是旁路证据。
