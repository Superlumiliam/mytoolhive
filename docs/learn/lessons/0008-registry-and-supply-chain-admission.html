第 8 课：Registry 是目录，准入是多道门

校准日期：2026-07-17 · 预计 25 分钟 · 唯一目标：给定一个 server 名称或 image reference，你能追踪 provider lookup、metadata、provenance verification、RunConfig policy gate 与 pull，并判断每道门拒绝什么、默认是否 fail-open。

任务钩子

“它在企业 registry 里，所以可以安全运行”是危险推理。Registry 可以提供 image、transport、permissions 和 provenance 元数据，但 provider 数据的来源可信度、签名验证模式、运行策略和最终拉取对象是不同责任。

发现

Provider 把名称解析为 container 或 remote metadata；当前 lookup 的任何错误都会把输入回退为直接 image reference，不只是真正的 not-found。

验证

Image verifier 比对 provenance；默认 warn 继续、enabled 拒绝、disabled 跳过。

策略

Runner PolicyGate 评估完整 RunConfig；默认 gate 是 allow-all。Registry mutation 还有另一套独立 PolicyGate。

从名字到执行对象

serverOrImage ├─ npx:// uvx:// go:// → build local image (no registry metadata) └─ registry lookup ├─ container metadata → image + transport/args/permissions/provenance ├─ remote metadata → RemoteURL path └─ not found → direct image reference fallback │ VerifyImage(disabled|warn|enabled) │ build RunConfig + eager PolicyGate │ policy-before-pull (local image only) │ SaveState / detached handoff │ Runner policy gate again → runtime
先策略、后下载：EnforcePolicyAndPullImage 对本地非 remote workload 先调用 active RunConfig gate，拒绝时不下载 image；Kubernetes 跳过本地 pull，由 kubelet 拉取，但 Runner 仍会再次检查创建策略。

这还不是 verified pull：VerifyImage 校验 tag 后不返回或固定 digest，后续 pull 仍使用原 tag；tag 可在两步之间变化，本地已有/拉取失败回退也没有与已验证 digest 对账。应把当前行为称为 best-effort provenance check，而不是“最终运行对象已加密绑定”。

Provider 优先级不是“信任等级”

优先级来源关键边界
1Registry API URL（cached）可配置 OAuth；cache、认证失败和 schema conversion 都影响结果。
2Remote static JSON URL不使用 API provider 的 auth；private-IP 开关影响 SSRF 边界。
3Local JSON file信任落在文件写权限、schema 与发布流程。
4Embedded registry随 ToolHive 版本交付；不是实时企业 policy。

两个“policy gate”不要混用：pkg/registry/policy_gate.go 控制 registry 配置的 update/delete；pkg/runner/policy_gate.go 控制 server create。两者默认都 allow-all，注册一个不会自动启用另一个。

走读 8 个锚点

  1. pkg/registry/factory.go：provider precedence、interactive auth 与 singleton cache。
  2. pkg/registry/provider.go：目录能力只有 get/list/search，不是执行授权接口。
  3. pkg/registry/provider_cached.go：API cache、disk fallback 与 auth error 处理。
  4. pkg/runner/retriever/retriever.go：protocol build、lookup fallback、VerifyImage、policy-before-pull。
  5. cmd/thv/app/run_flags.go：retriever metadata 如何变成 builder options。
  6. pkg/runner/policy_gate.go：eager 与 Runner 内重复 create check。
  7. pkg/registry/policy_gate.go：registry mutation 的独立门。
  8. pkg/container/images：pull/local existence 与 keychain 的实际边界。

先预测，再展开

registry 查询失败，一定拒绝吗？

不会。当前 handleRegistryLookup 对任何 GetServer 错误都回退为直接 image reference，连服务/认证错误也不区分；若 verification 为 enabled 且无 provenance 才会拒绝。企业准入不能只依赖“目录中是否存在”。

warn 模式验证失败后还能运行吗？

对 unsigned/provenance mismatch 会记录 warning 并继续；它还是当前默认值，适合迁移可见性，不是强制准入。强制失败需 enabled。

policy check 在所有副作用之前吗？

不是。普通本地 image 的 helper 是 policy-before-pull，但 npx:///uvx:///go:// 会先下载/构建本地镜像，再形成 RunConfig 并检查 gate。多次 gate 也必须幂等且不能替代副作用前准入。

Operator 会复用同一 Registry 验证链吗？

不会。MCPServer CR 直接给出 image，controller 不走 ToolHive provider、VerifyImage 或这两套 package gate；集群可信准入依赖 digest、admission policy 与镜像验证控制器。MCPRegistry CR 也不会自动成为 MCPServer allowlist。

测试取证

  • pkg/registry/factory_test.go：provider precedence、singleton/reset 与 custom config。
  • pkg/registry/schema_validation_test.go、convert_test.go：输入 schema 与 API conversion。
  • pkg/registry/provider_cached_authbug_test.go：认证失败不能被 stale cache 静默掩盖。
  • pkg/runner/retriever/retriever_test.go：lookup fallback、verification、policy拒绝时不 pull、Kubernetes/remote skip。
  • pkg/runner/policy_gate_test.go 与 pkg/registry/policy_gate_test.go：两个 gate 的默认和注册行为。

3 分钟门禁分诊

选择最直接的门；三个选项均为 6 个字符。

A. 名称解析成了错误 image。

B. image 签名主体与 metadata 不符。

C. 已验证 image 申请了不允许的 writable mount。

5 分钟实作：写一份准入证据链

为一个 registry server 写六行：① provider/source；② metadata 中的 image 与 provenance；③ verification mode；④ direct-image fallback 是否允许；⑤ create policy 使用哪些 RunConfig 字段；⑥ 拒绝发生在 pull 前还是后。把答案发给教师获得反馈；展示出理解后才写学习记录。

一手资料

主读：Retriever 与 Registry Factory。背景见 Registry System；准入事实以当前 provider、verifier、gate 与测试为准。
