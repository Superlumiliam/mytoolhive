第 3 课：把一次 thv run 追到真正运行

校准日期：2026-07-17 · 预计 25 分钟 · 唯一目标：当 thv run 失败或“看似成功但不可用”时，你能判断失败位于输入构建、状态交接还是长期执行，并直接定位下一份源码、日志与测试。

任务钩子

用户执行 thv run fetch 后 shell 很快返回，但客户端连不上 MCP server。你应该先看命令行错误、RunConfig、Proxy 日志，还是 container 日志？答案取决于请求走到了哪一个“提交点”。第 2 课已经建立 detached process 心智模型；这一课把它变成可复用的调试方法。

01

输入构建

解析目标与参数，选择 runtime，解析 registry/image，构造并校验 RunConfig，执行同步 policy gate 与 image pull。

02

状态交接

先保存不含解析后秘密的 RunConfig，再 re-exec thv start <name> --foreground，记录 status 与 PID。

03

长期执行

子进程从状态加载 RunConfig，重新注入本进程的 runtime，再装配 secrets、middleware 与 transport，启动、探测并持续监控 workload。

关键不变量：父进程的成功边界是“detached 子进程已启动”，不是“server 已 ready”。RunWorkloadDetached 在 spawner 返回 PID 后即可结束；后续 Runner.Run 的失败会出现在 Proxy 日志和 workload status 中。

两次进入 thv，一次状态交接

进程 A（短命控制） runCmdFunc → runSingleServer → BuildRunnerConfig → SaveState → RunWorkloadDetached │ re-exec: thv start NAME --foreground ▼ 进程 B（长期 supervisor） restartCmdFunc → RestartWorkloads → loadRunnerFromState → RunWorkload → Runner.Run │ secrets/middleware → runtime.Setup → transport.Create/Start → readiness/status

提交点：SaveState 是两个进程共享意图的边界，但 runtime 对象不会随 JSON 跨进程持久化，子进程会在 loadRunnerFromState 重新注入。若保存成功但 spawn 失败，RunConfig 可能已经存在，但 PID 不应被记录；当前 PID 以 status JSON 的 process_id 保存，独立 PID 文件主要是迁移兼容路径。

测试不是“按文件读完”，而是按边界取证

  • pkg/runner/retriever/retriever_test.go：用 TestEnforcePolicyAndPullImage 确认 policy 拒绝时不 pull，以及拉取失败如何同步传播。
  • pkg/runner/config_builder_test.go：确认 option 合并、transport、permission profile、env 与 schema 等 RunConfig 契约。
  • pkg/workloads/manager_test.go：重点看 RunWorkloadDetached_SpawnerSuccess、SpawnerError 和 RunWorkload 重试。
  • pkg/runner/runner_test.go：用 TestWaitForInitializeSuccess 确认 readiness 的成功、超时、认证与取消语义。
  • cmd/thv/app/run_test.go 当前主要覆盖 remote name；不要把它误当作整条 thv run 主链已有完整单元测试的证据。

立即检索

先在脑中作答，再展开反馈。

1. 为什么必须先 SaveState，再启动 detached 子进程？

子进程通过 thv start NAME --foreground 重入，并从 state 恢复 RunConfig。若先 spawn，子进程可能在配置尚未持久化时读取，形成竞态或启动失败。

2. image pull 属于长期 supervisor 的工作吗？

本地普通路径中，BuildRunnerConfig 在父进程通过 EnforcePolicyAndPullImage 先执行 policy gate 再 pull，使拒绝和拉取错误同步返回给用户；长期进程随后负责实际 runtime/transport 生命周期。

3. readiness 探测超时一定让 Runner 退出吗？

不一定。当前实现记录 warning 后继续，以保持兼容性；所以“探测告警”与“transport 启动失败”是不同契约，应以 TestWaitForInitializeSuccess 和调用处共同判断。

3 分钟故障分诊

选择首要调查阶段。三个选项均为 6 个字符，避免长度泄题。

A. 命令立即报 endpoint-prefix must start with '/'，没有 RunConfig。

B. RunConfig 已出现，但命令报告 failed to start detached process，没有 PID。

C. shell 已返回成功，随后 status 变为 Error，Proxy 日志显示 transport start 失败。

5 分钟实作：为一个失败画“最后成功点”

假设 thv run fetch 返回成功，但一分钟后 thv status fetch 为 Error。写五行：① 最后一个由父进程保证成功的事件；② 子进程如何找到 RunConfig；③ 你先看的日志；④ 你会在 Runner.Run 中检查的两个边界；⑤ 最接近该失败的测试或测试缺口。把答案发给教师，我会按“进程是否分清、提交点是否准确、证据是否邻近、测试是否真覆盖”逐项反馈；通过后才写入学习记录。
