第 5 课：Transport 决定 Proxy 的工作

校准日期：2026-07-17 · 预计 25 分钟 · 唯一目标：给定 server 实际说的协议、client 需要的协议和一个故障症状，你能判断 ToolHive 应使用透明转发还是协议桥接，并定位 endpoint 与 session 的所有者。

任务钩子

一个容器只通过 stdin/stdout 读写 JSON-RPC，客户端却访问 POST /mcp；另一个容器自己监听 /mcp。两者都能在 ToolHive 外暴露 HTTP，但 Proxy 的责任完全不同：前者必须实现客户端侧 MCP transport，后者主要转发 server 已实现的 HTTP transport。

STDIO

协议桥接

ToolHive attach 容器 stdin/stdout，解析 newline-delimited JSON-RPC，并用 protocol-specific proxy 对客户端暴露默认 /mcp 或旧式 /sse + /messages。

SSE

HTTP 转发

server 自己实现 SSE。ToolHive 的 HTTPTransport 把请求交给 transparent proxy，并跟踪 session、重写 endpoint、应用治理中间件。

STREAMABLE

HTTP 转发

server 自己实现 Streamable HTTP。Proxy 保留 HTTP/MCP 语义并追踪 Mcp-Session-Id；本地、remote 与多副本场景可改变 target。

不要混淆两个维度：Transport 描述 server 侧协议；只有当它是 stdio 时，ProxyMode 才选择 client 侧是 SSE 还是 Streamable HTTP。stdio 的默认 ProxyMode 是 streamable-http。

Factory 的真实分流

RunConfig.Transport ├─ stdio │ └─ StdioTransport → AttachToWorkload │ ├─ ProxyMode streamable-http → streamable.HTTPProxy → client /mcp │ └─ ProxyMode sse → httpsse.HTTPSSEProxy → client /sse + /messages ├─ sse │ └─ HTTPTransport → transparent.Proxy → server HTTP endpoint └─ streamable-http └─ HTTPTransport → transparent.Proxy → server HTTP endpoint

“透明”不等于“无知”：transparent proxy 通常不把 HTTP server 重新实现成另一个 MCP transport，但仍会执行 method/body 限制、session 检测和路由、SSE endpoint 重写、远端 path/query 保留、健康检查以及 middleware。修改它仍可能改变协议与安全语义。

按执行顺序走读 7 个锚点

  1. pkg/transport/types/transport.go：区分 TransportType、ProxyMode、EffectiveProxyMode 与 Transport/Proxy 接口。
  2. pkg/runner/runner.go：看 runtime.Setup 如何先给出 container name / TargetURI，再交给 transport factory。
  3. pkg/transport/factory.go：验证三种 TransportType 实际实例化哪一种 transport。
  4. pkg/transport/stdio.go：看 attach、proxy mode 分流、stdin/stdout message pump 与 container monitor。
  5. pkg/transport/http.go：看本地 TargetURI 与 RemoteURL 如何收敛为 transparent proxy target。
  6. pkg/transport/proxy/transparent/transparent_proxy.go：找 reverse proxy、session、health、routing 与 catch-all handler。
  7. pkg/transport/session/manager.go：确认 TTL、storage 和 typed session 的生命周期。

检索题：先预测，再展开

native streamable-http server 的 ProxyMode=SSE 会让客户端看到 /sse 吗？

不会。NormalizeProxyMode/EffectiveProxyMode 对直接 HTTP transport 以 transport 本身为准；ProxyMode 只决定 stdio 的客户端侧协议。

remote URL 带 /v2/mcp?toolsets=core 时，target 只保留 host 吗？

HTTPTransport 用 scheme+host 建立 target，同时把 remote base path 和 raw query 作为 transparent proxy options，相关测试锁定 path/query 不应静默丢失。

session storage 只是缓存，丢了也不影响路由吗？

不能一概而论。它保存 session 与 backend/路由元数据；单副本默认内存存储，多副本需要共享存储才能让后续请求找到一致 backend。分布式细节留到第 15 课。

thv proxy stdio 也会进入 Factory 的 StdioTransport 吗？

不会。它是相反方向的独立桥：本地 stdio façade 连接远端 SSE/Streamable server，走 cmd/thv/app/proxy_stdio.go 与 pkg/transport/bridge.go，不应和“HTTP client → ToolHive → container stdio”的 StdioTransport 混为一谈。

测试是协议契约

  • pkg/runner/config_test.go：NormalizeProxyMode 和 transport/port 组合。
  • pkg/transport/stdio_test.go：JSON-RPC parsing/forwarding、reattach、并发与 factory 字段传递。
  • pkg/transport/proxy/streamable/streamable_proxy_spec_test.go：initialize session header、DELETE、stale session、notification 与并发 sessionless 请求。
  • pkg/transport/proxy/transparent/transparent_test.go：header/body session 检测、endpoint rewriting、health 与停止语义。
  • pkg/transport/proxy/transparent/remote_path_test.go：remote path/query 转发不丢失。

3 分钟路径判断

选择最先负责修复的边界；三个选项均为 6 个字符。

A. stdio server 的客户端初始化 POST /mcp 得到错误 session header。

B. ingress 前缀下 native SSE endpoint event 返回了错误外部路径。

C. 两个 proxy 副本间切换后，已初始化 session 的后续请求找不到 backend。

5 分钟实作：设计一条 transport 诊断记录

任选一个连接失败，写六行：① server 实际协议；② client 期望协议；③ Transport；④ 若为 stdio，ProxyMode；⑤ client endpoint 与 upstream target；⑥ session ID 由谁产生、存在哪里。把答案发给教师，我会按“两个协议面是否分清、endpoint 是否准确、session 所有权、证据路径”反馈；展示出理解后才写入学习记录。
