第 14 课：同一次调用可以经过三个令牌边界

校准日期：2026-07-17 · 预计 30 分钟 · 唯一目标：给定一次受保护的 tools/call，你能标出每一跳使用的 token、issuer、audience/resource、主体与策略，并区分入站验证、会话主体绑定、授权决策和出站令牌转换。

任务钩子

客户端 token 能通过 vMCP，不代表 backend 也应接受它；同一个 sub 能恢复 session，也不代表旧 token 无需重新验证。OAuth 故障只有把“谁给谁签、给哪个资源、在哪一跳消费”写清，才能停止在 audience、session ID 和 backend token 之间猜测。

Client obtains access token T_front iss = trusted issuer / embedded ToolHive AS aud = public MCP resource │ Authorization: Bearer T_front ▼ Incoming OIDC validator signature/JWKS or introspection + iss/exp/aud → Identity{(iss,sub), claims, Token, optional UpstreamTokens} ├─ session binding compares fresh (iss,sub) ├─ Cedar admission decides List/Call/Read/Get ▼ Outgoing strategy selected per backend unauthenticated | header | upstream_inject | token_exchange | AWS | XAA | OBO* │ exchange/inject T_backend for target audience/scopes ▼ Backend MCP endpoint → upstream API
四个独立判定：authentication 证明当前 token；session binding 证明当前主体等于 session 创建者；authorization 判断该主体能否执行动作；outgoing auth 决定 vMCP 怎样向特定 backend 出示凭据。任一层成功都不能替下一层背书。

Issuer、Audience、Resource、Scope

字段回答ToolHive 边界
issuer谁签发/声明 token必须与可信配置和 discovery/JWKS 关系一致；不是 backend URL 的别名
audiencetoken 给谁消费MCPOIDCConfig 的 audience 在 consumer ref 上配置；API 注释要求每服务唯一，但没有跨 CR 全局唯一性校验
resourceOAuth 请求/metadata 指向哪个受保护资源RFC 8707/9728 的公开 resource URL；embedded auth server 路径要求 ref 的 audience 与 resourceUrl 相等
scope请求/授予哪类权限用于 discovery、授权请求或 token exchange；不能替代服务端 action/resource 授权

共享 OIDC，不共享 audience：MCPOIDCConfig 保存 issuer、JWKS/introspection、client/CA 等共享事实，MCPServer/MCPRemoteProxy/VirtualMCPServer 的同 namespace reference 提供各自 audience、resourceUrl、scopes。namespace 隔离不等于 audience 自动唯一。

Embedded Auth Server 是联邦入口，不是验证替身

MCPServer / MCPRemoteProxy

authServerRef 只能指向同 namespace、type=embeddedAuthServer 的 MCPExternalAuthConfig；同时仍需 OIDCConfigRef，让 workload 验证 embedded server 签发的 access token。

VirtualMCPServer

没有 authServerRef；使用内联 spec.authServerConfig 配置 embedded server，并仍配置 incoming OIDC。上游 IdP 凭据可存于 auth server storage，ToolHive JWT 的内部 tsid 只是查找这些凭据的指针。

tsid 不是什么

它不是 MCP Mcp-Session-Id，也不是 vMCP identity binding。validator 可用它加载 provider tokens 到 Identity.UpstreamTokens，随后会从对外 claims/序列化视图中剔除该内部值。

没有 embedded AS 的直接 IdP 路径中，入站 bearer 本身进入 Identity.Token，可作为 token exchange 的 subject；不会凭空出现 ToolHive JWT 或 tsid。若 resourceUrl 未设置，Operator resolver 可能采用集群内 Service URL；公网 Ingress/Gateway 部署应显式写客户端实际连接的公开 resource。

会话绑定不保存认证证明

  • vMCP 把 session owner 编码为 iss + NUL + sub；该值明文存储，是 PII 但不是 credential，也没有 exp/nonce/freshness。
  • 每个请求先验证当前 token，再从 fresh Identity 比较绑定；同 issuer/subject 的刷新 token可继续 session，不同主体 fail closed。
  • 匿名 session 只接受匿名 caller；后来带 token 访问会被当作 session-upgrade attack 拒绝。
  • Operator 当前仍创建并注入 VMCP_SESSION_HMAC_SECRET，但 #5306 后的 runtime identity-binding 模型不使用它；不能把存在 Secret 当作 HMAC 已保护 session。

三种“会话”：Mcp-Session-Id 是 MCP 协议句柄；JWT tsid 是上游凭据存储指针；(iss,sub) binding 是 session owner 约束。三者不可互换。

出站凭据选择

策略凭据来源治理重点
token_exchange当前 Identity.Token 或命名 upstream provider tokenRFC 8693 token URL、subject token type、target audience/scopes、per-user cache
upstream_injectembedded AS 保存并由 tsid 取回的 upstream tokenprovider 选择、刷新、最小转发
header/bearerSecret/env 或固定配置不把 secret 写入 ConfigMap/log，限制 backend 使用范围
AWS STS / XAA主体 token/identity assertion 经专用交换target、签名、缓存与协议专属语义
OBO当前用户主体 token上游 OSS build 只有 EnterpriseRequired stub；未注册企业实现时不可运行

默认不是拒绝：未配置 backend auth 时，unauthenticated 可能是不带凭据调用。embedded 路径还应在 middleware 中 swap/remove 原 ToolHive JWT，再注入 upstream/exchanged credential，不能把前端 bearer 原样跨 audience 转发。vMCP discovered 模式可能凭 RBAC 读取 Secret 并放入进程内存；“不进 ConfigMap”不等于“永不进内存”。

3 分钟边界分诊

三个选项均为 6 个字符。

A. client token 的 aud 指向另一个 MCPServer。

B. 有效 token 的另一个用户复用 Mcp-Session-Id。

C. vMCP 已接受用户，但 backend 需要不同 audience。

5 分钟实作：令牌账本

为一次 tools/call 写八行：① T_front issuer；② audience/resource；③ validation method；④ (iss,sub) binding；⑤ Cedar action/resource；⑥ outgoing strategy/subject token；⑦ target audience/scopes；⑧ T_backend consumer。把答案发给教师获得反馈；展示出理解后才写学习记录。
