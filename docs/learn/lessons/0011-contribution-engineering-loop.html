第 11 课：验证计划从改动面推导

校准日期：2026-07-17 · 预计 25 分钟 · 唯一目标：面对一个 ToolHive diff，你能从受影响的契约推导最小但充分的生成、测试、lint、兼容性与人工验证证据，并写成可复核的 PR test plan。

任务钩子

“我跑过测试”不是证据计划。CLI 参数、Go 接口、CRD 字段、Helm 模板和文档各自会触发不同生成物与 CI；漏跑一种，常常不是代码编译失败，而是提交了陈旧文档、mock 或 schema。

Read issue / claim work → define one logical change + compatibility boundary → code and adjacent unit tests → regenerate affected artifacts → run smallest relevant task checks → perform appropriate manual verification → expand to integration / E2E by risk → review diff, generated files and API surface → signed-off, focused commits → PR: why + what + exact evidence + limitations → CI + reviewer feedback → revise
统一入口：使用 task 目标，而不是自行拼 go test、go build 或 lint 命令。Taskfile 已编码平台差异、race、排除目录、生成依赖与构建 flags；例如 task test 会先依赖 task gen，task test-e2e 会先依赖 build。

task all 不是完整 CI：它只聚合 lint、unit test 与 build，不含 license、docs/codegen 漂移、安全、Helm、integration、E2E 或 Operator checks。先跑针对性任务，再让 PR CI 独立复核整张证据图。

从变更面选择证据

改动面最小证据容易遗漏
普通 Go 逻辑邻近单测 + task test + task lint-fixrace、error path、mock 漂移
CLI / API handler上述 + task docs + 对应 API/CLI 用户路径；新功能同时补 API 与 CLI E2Edocs/cli、Swagger、人工验证
接口 / mock 来源task gen，提交预期生成 diff；再跑生成不得出现额外 diffCI 会再次生成并拒绝遗漏
Operator CRDtypes→task operator-generate；markers→task operator-manifests；任一 CRD change→根目录 task crdref-genv1beta1 兼容性与生成 schema/docs
Helm chartstask helm-unittest；文档用 task helm-docs / task docsCI 另做 lint/template 与生成漂移
跨组件行为task test-integration / task test-e2e + 手测Docker/Kind 前置与真实 transport

稳定 API 默认只允许加法：v1beta1 字段、类型、JSON tag、schema 类型、finalizer、shortName 和 scope 都有兼容承诺；新字段应 optional，新行为应 opt-in。api-break-allowed 是协调后的迁移出口，不是关闭误报的按钮。

三层评审契约

提交怎样让历史可读？

Subject 不超过 50 字符、首字母大写、祈使语气、无句号；body 解释 what/why。外部贡献的每个 commit 还要有 Signed-off-by trailer，满足 DCO。

PR 怎样让 reviewer 快速验证？

一个 PR 聚焦一个逻辑变化；团队预检采用更严的 400 code LOC/10 files（测试、文档、生成物除外），上游 CONTRIBUTING 则警告超过 1000 行可能被阻塞。标题小于 70 字符、祈使语气、无句号和 Conventional Commit 前缀；模板恰选一种 change type、至少记录一项真实验证，并删除不用的可选占位。

CI 为什么不是本地验证的替代品？

PR 工作流并行验证 spellcheck、license、lint、安全、测试、docs、codegen、charts、E2E、operator 等。它证明仓库级一致性，但发现问题更晚；本地按风险缩短反馈环，CI 再作独立复核。

走读 8 个锚点

  1. CONTRIBUTING.md：issue、DCO、测试、PR、commit 与 API stability。
  2. Taskfile.yml：所有规范化 build/gen/lint/test/docs 入口。
  3. cmd/thv-operator/Taskfile.yml：operator build/test/manifests/CRD docs；CRD types 后跑 operator-generate，markers 后跑 operator-manifests，CRD 变更还要从根目录跑 crdref-gen。
  4. .claude/rules/testing.md：pkg 单测、CLI E2E、Operator/Chainsaw 与测试质量。
  5. .github/pull_request_template.md：why/what、test plan、compatibility。
  6. .github/workflows/run-on-pr.yml：仓库级 CI fan-out。
  7. .github/workflows/verify-gen.yml：生成后必须无未提交 diff。
  8. .github/workflows/api-compat.yml：已发布 CRD schema 兼容检查。

3 分钟证据分诊

为每个改动选择最先暴露其特有风险的检查；三个选项均为 6 个字符。

A. 修改被 mockgen 引用的接口。

B. 修改内部状态映射分支。

C. 修改 MCPServer v1beta1 字段。

5 分钟实作：写 test plan

任选一个真实 diff，写七行：① 用户/契约变化；② 邻近单测；③ 生成任务；④ lint/build；⑤ integration/E2E/手测；⑥ API/升级风险；⑦ 未执行项与原因。再对照 PR template，只勾实际证据。把答案发给教师获得反馈；展示出理解后才写学习记录。
