第 1 课：ToolHive 是治理平台，而不只是容器启动器

预计 25 分钟 · 唯一目标：你能把一个未知 MCP server 的企业治理职责映射到 ToolHive 的代码边界。

任务钩子

某团队希望把一个陌生的 MCP server 交给 300 名员工使用。“把镜像跑起来”只回答了执行问题。企业还必须回答：来源能否信任？拿到什么权限？谁能调用哪些工具？凭据如何处理？如何审计和停止？如何在集群中持续保持期望状态？

ToolHive 的平台价值，就是把这些答案组织成一个闭环。打开 治理闭环速查，用一分钟扫一遍六个环节。

五个核心代码边界

  1. Registry：发现与准入；不是单纯搜索目录。
  2. RunConfig + Runner/Workload：把治理意图变成可验证、可执行、可管理的 workload。
  3. Runtime + Permissions：用容器与权限策略建立执行隔离。
  4. Proxy + Transport + Middleware：在流量边界执行协议适配、身份、授权、过滤、审计和遥测。
  5. Operator：在 Kubernetes 中以 reconcile 持续收敛期望状态。
关键不变量：workload 不是 container 的同义词；它包含 server、proxy、配置和可管理状态。只盯容器实现会漏掉治理主体。

像带新同事一样走读代码

这次不求读懂所有实现，只建立导航肌肉。依次打开并回答一个问题：

  1. cmd/thv/app/run.go：runCmdFunc 如何区分 registry name、image、protocol、config 和 remote URL？
  2. 同文件的 runSingleServer：container runtime 和 workload manager 在哪里创建？这暴露了什么依赖边界？
  3. pkg/workloads/manager.go：读 Manager 接口。为什么 stop/delete 返回 CompletionFunc？
  4. pkg/runner/runner.go：只定位 Runner.Run，列出它装配的三个主要职责。
  5. pkg/transport/factory.go：transport 的选择为什么应该集中在 factory 边界？

不要顺着每个函数无限下钻。先用 代码地图 记录“入口、接口、实现、测试”四类位置。

立即检索

先在脑中作答，再展开反馈。

1. Registry 已审核镜像，是否意味着运行时无需 permission profile？

否。供应链准入与运行时最小权限是不同信任边界；前者回答“允许什么进入”，后者回答“进入后能做什么”。

2. 在 HTTP 请求到达 MCP server 前实施 tool authorization，最自然的边界在哪里？

Proxy 承载的 middleware 管线。它位于 client 与 server 之间，能统一执行认证、授权、过滤和审计。

3. 为什么 Operator 必须进基础课程，而不是因为复杂就全部放高阶？

因为声明式 reconciliation 是企业集群治理的主路径。基础只要求掌握最小 CRD→resource→status 主链；复杂 cross-resource graph 留到高阶。
