第 12 课：聚合视图与路由表是两个契约

校准日期：2026-07-17 · 预计 30 分钟 · 唯一目标：给定多后端工具清单与治理意图，你能选择 prefix/priority/manual 策略，并分别写出客户端广告目录和会话路由表的可验证预期。

任务钩子

客户端看见 github_create_issue，backend 实际只认识 create_issue。vMCP 不只是拼接 JSON：它必须稳定保存“广告名 → 原名 → backend target”的映射，并确保同一身份看到的能力与最终可调用能力一致。

groupRef or static backends → Discover backends (inline | discovered) → parallel ListCapabilities (tools/resources/prompts) → tool overrides → conflict resolution (prefix | priority | manual) → advertised capability view + full routing table → health filter + identity-aware cache + admission filter → MCP List* response CallTool(advertised name) → admission decision → routing entry: backend ID + original name + target/auth → backend client call → response
两个契约：广告视图控制客户端上下文；路由表控制实际执行。过滤或 excludeAll 可以不向客户端展示 backend 工具，但实现仍保留内部路由，供 composite tools 使用；真正的安全边界还必须在每次 List/Call/Read/Get 的 admission 上执行。

Group 不是授权边界：它只定义候选 backend 集合。VirtualMCPServer CR 的 groupRef 指向同 namespace MCPGroup，incomingAuth 必须显式配置（无需认证也写 anonymous）；能入组不等于任意身份都能调用。

三种重名策略

策略广告结果失败/回退语义
prefix给所有工具加 workload 前缀，不只重名项默认格式 {workload}_，来源最清楚
priority非冲突工具保留原名；冲突由 priorityOrder 最靠前者胜出冲突候选都不在顺序中时回退 prefix，避免静默丢失
manual每个冲突候选按 override 映射公开名遗漏冲突或 override 后再次碰撞会报错

Per-workload override 在冲突解析前生效。无论广告名怎样变化，routing entry 都必须保留 backend 实际的 original capability name。

六层责任矩阵

层决定什么典型故障
发现有哪些 backend、URL、transport、auth contextgroup 成员缺失、CR status/URL 未就绪、RBAC Forbidden
查询每个 backend 暴露的 tools/resources/prompts初始化失败、单后端超时；部分失败会降级继续，全部失败才终止
冲突重名工具的广告名与赢家prefix 格式不稳、priority/manual 配置漏项
广告当前身份看见哪些能力filter/exclude、health、authz 让工具不可见
路由广告名还原到 backend 原名和 target重命名后映射丢失、backend ID 错配
执行最终 admission、outgoing auth、backend 调用列表可见但调用被拒、token/网络/后端错误

冲突解析目前不对称：prefix/priority/manual 解决的是 tool 名称；resources 与 prompts 会被合并，但没有同等的冲突解析策略。不能从“工具无重名”推断 URI/prompt 名称也已治理。

Inline 与 discovered 不是同义配置

inline/static 模式

Operator 在 reconcile 时仍从 MCPGroup 解析 backend，再把 ID、URL、transport、CA/auth 结果嵌入 ConfigMap；Pod 运行时无需读取 Kubernetes discovery API。至少一个 backend 必须可转换。它缩小运行时 RBAC，但不是“完全不发现”。

discovered 模式

vMCP Pod 内 watcher 运行时读取同 namespace 的 MCPServer、MCPRemoteProxy、MCPServerEntry 等并维护 DynamicRegistry；因此需要更宽 RBAC，/readyz 还要等待 informer cache sync。Secrets 不直接 watch，轮换可能依赖引用对象变化或 Pod 重启。

刷新与缓存

core 自身按调用重新从 registry 聚合并用健康状态过滤；Serve 侧缓存按 identity/forwarded credential/backend ID set 键控，默认 TTL 30 秒，错误不缓存。同一 ID 的 URL/auth 更新可能等到 TTL，而 backend ID 集变化会换 key。

故障隔离的真实含义

  • 能力查询并发上限为 10；单个 backend 查询失败会记录并继续，零个成功才返回错误。
  • health monitor 启用时可把不健康 backend 排除出能力视图；monitor 启动失败会被记录并退回“不做 health filter”，不是进程必然启动失败。
  • /health 证明 vMCP 服务面可响应，不等于所有 backend、所有身份、所有工具都可调用。
  • Serve 的 MultiSession 保存会话广告工具与不可变 RoutingTable；core 可按调用重新聚合，但不能把共享可变 router 当跨 session 全局真相。
  • 本地用户入口优先是 thv vmcp；独立 cmd/vmcp 是兼容/高级入口，Kubernetes 主入口是 VirtualMCPServer CR。

刷新有时间裂缝：已建立 session 的广告能力是注册快照；新 session 才自然吸收新增 backend。调用 handler 又按 core 当前视图路由，因此旧 session 可能仍展示刚删除的工具，而 call 在 cache 刷新后返回 NotFound。配置中的 partialFailureMode 当前没有接入这条运行路径，实际行为仍是单 backend best-effort、全部失败报错。

走读 8 个锚点

  1. pkg/vmcp/config/config.go：group、static backends、aggregation、auth、operational。
  2. pkg/vmcp/aggregator/discoverer.go：group/static backend discovery。
  3. pkg/vmcp/aggregator/default_aggregator.go：并发查询、冲突、广告视图与 routing table。
  4. pkg/vmcp/aggregator/conflict_resolver.go：prefix/priority/manual factory。
  5. pkg/vmcp/aggregator/caching_aggregator.go：identity-aware TTL/LRU。
  6. pkg/vmcp/core/core_vmcp.go：health filter、admission 与 per-call router。
  7. pkg/vmcp/router/session_router.go：广告名到 backend target 的执行映射。
  8. cmd/thv-operator/controllers/virtualmcpserver_controller.go：inline/discovered RBAC 与部署。
