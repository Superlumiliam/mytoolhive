第 6 课：Middleware 顺序就是安全语义

校准日期：2026-07-17 · 预计 25 分钟 · 唯一目标：面对一条 middleware 配置或新增 middleware，你能推导真实请求顺序，指出它依赖哪些上游 context/headers，并判断拒绝、变换、审计和 backend egress 的正确相对位置。

任务钩子

把 authz 移到 authn 之前，策略就读不到可信身份；把 token injection 放在 audit 之前，审计可能观察到错误凭据；把 body limit 放到 parser 之后，恶意大 body 已被读入内存。middleware 顺序不是美学，它决定谁能看见什么、谁能修改什么、失败是否留下证据。

入口防护

body limit 最外层；Origin 校验紧随其后，尽早拒绝超大 body 与 DNS rebinding 输入。

身份与决策

authn 建立 identity，parser 建立 MCP method/tool context，mutate 先于 validate，authz 才能基于可信上下文决策。

出口变换

audit/authz 后再做 AWS signing、header forward 或额外 egress 变换，尽量贴近 backend，避免后续修改使签名或凭据失真。

“逆序包裹”不等于“逆序执行”

slice: [A, B, C] for i = 2..0: handler = middleware[i](handler) 结果: A(B(C(backend))) 请求: A → B → C → backend 响应: backend → C → B → A
代码判断法：proxy 虽然从 slice 尾部开始包裹 handler，但 index 0 最后包在最外层，所以第一个配置在请求时最先执行。不要照抄 WithMiddlewareFromFlags 中“first effectively last”的旧注释；以三个 proxy 的实际循环和顺序测试为准。

Populate / Operator 路径的安全骨架

相对位置代表 middleware必须守住的不变量
最外层body-limit → origin在 auth/parser 读取 body 或执行业务前拒绝资源耗尽与非法 Origin。
身份入口auth → upstream-swap / token-exchange / strip-auth先验证客户端身份，再转换或移除发往 upstream 的凭据。
MCP 语义tool filters → parser → rate-limit → mutating → validating需要 MCP context 的组件必须位于 parser 之后；mutate 必须先于 validate。
决策与证据usage/telemetry → authz → auditauthz 看到身份与有效请求；audit 位于其内侧，因此 authz 提前拒绝时未必进入 audit。必须用实现测试确认要记录的事件。
backend egressAWS STS → header-forward → additional middleware签名和 upstream header 尽量接近 backend，禁止把 raw secret 放入可序列化参数。
最内层recovery只捕获 handler 与比它更内层的 panic；无法捕获外层 middleware 自己的 panic。

存在两条装配路径：CLI flags 可预先填充 MiddlewareConfigs；Operator/通用路径由 PopulateMiddlewareConfigs 从 typed RunConfig 字段生成。Runner 随后统一补 header-forward、prepend Origin、确保 body-limit，再逐项调用 factory。两条路径目前并非完全同构，变更必须覆盖两侧测试。

当前实现审计点：有 Origin 时，Populate 已加入的 body-limit 可能被 Runner 再次 prepend，形成 body-limit → origin → body-limit；预填的 operator header-forward 也可能在 Runner 解析秘密后再次 append。它们是需要组合测试锁定并修复的现状，不是应当模仿的设计。

走读 7 个锚点

  1. pkg/runner/middleware.go：列出 supported factories，追踪 Populate、Origin、body limit、header-forward 与 recovery。
  2. pkg/runner/config_builder.go：检查 WithMiddlewareFromFlags 的独立装配路径及其 TODO。
  3. pkg/runner/runner.go：确认 secrets 先解析、configs 后补全、factory 顺序创建并传给 transport。
  4. pkg/transport/proxy/transparent/transparent_proxy.go：验证 index 0 如何成为 catch-all handler 的最外层。
  5. pkg/transport/proxy/streamable/streamable_proxy.go：核对 stdio→Streamable 的同一 reverse-wrap 语义。
  6. pkg/transport/proxy/httpsse/http_proxy.go：注意 MCP endpoints 经过链，但 health/metrics/discovery 不完全经过同一链。
  7. pkg/transport/types/transport.go：理解 Config 与实际 Middleware instance/handler 的分工。

先预测，再展开

recovery 放在 slice 最后，能捕获 body-limit 的 panic 吗？

不能。它是最内层 wrapper，只包住 backend；body-limit、auth 等外层 middleware 的 panic 不会穿过 recovery。当前注释和测试应明确这项有限保证。

/health、/metrics 和 OAuth discovery 都经过 authz 吗？

不应假定。proxy mux 将这些专用 handler 与受 middleware 包裹的 MCP handler 分开挂载；评审暴露面时必须逐 endpoint 看路由，而不是只看 middleware slice。

只在 PopulateMiddlewareConfigs 调整顺序就覆盖 CLI 吗？

不一定。CLI 的 WithMiddlewareFromFlags 会预填 slice，使 Runner 跳过 Populate；必须检查两条组装路径以及 Runner 的统一补丁步骤。

standalone thv proxy 也使用这条完整链吗？

不会。它不进入 Runner，而是在 cmd/thv/app/proxy.go 手工组装较短的 body-limit、origin、auth、token/header 链；没有 parser/filter/authz/audit/telemetry/recovery。不要把 Runner 的链当作所有 Proxy 的全局事实。

mutating webhook 之后的 authz 一定看到变更后的 arguments 吗？

当前 parser 先把解析结果放入 context，而 mutating middleware 替换 request body 后没有同步刷新该 context；后续 authz 可能仍读取旧 arguments。现有集成测试证明 validating/backend 看到新 body，但没有锁定 authz 输入，这是很好的贡献测试候选。

测试锚定顺序

  • pkg/runner/middleware_test.go：body-limit outermost、AWS STS、strip-auth 冲突与相对位置、full coverage。
  • pkg/runner/webhook_integration_test.go：真实 handler 包裹后 mutating → validating → authz → backend 的行为。
  • pkg/transport/proxy/streamable/body_limit_test.go：大 body 在 parser 前得到 413。
  • pkg/transport/middleware/origin/origin_test.go：allowlist 与 DNS rebinding 防护。
  • 各 middleware 邻近测试：不要只证明“slice 中存在”，还要证明 context/header、拒绝和响应路径。
