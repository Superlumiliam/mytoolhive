部署形态与信任边界速查

不变量：部署形态改变的是控制入口、权限身份、状态事实源和漂移修复机制。它不应改变客户端请求必须经过 Proxy 治理边界这一原则。

四问法

1
谁提交意图？
shell、HTTP 调用者，还是 Kubernetes API 中的 CR？
2
谁持有权限？
谁能调用 container socket 或 Kubernetes API？
3
谁是事实源？
本地状态文件，还是 spec/status 与子资源？
4
谁修复漂移？
单次命令、detached supervisor，还是持续 reconcile？

危险信号

  • 把 API server 当作所有本地 Proxy 的父进程。
  • 把“能访问 API”误当作“有权执行所有 workload 操作”。
  • 把 status 当期望状态，或把 spec 当实时健康证据。
  • 给 controller 集群管理员权限，却没有逐项说明需要。
  • 只创建 Kubernetes 对象，却没有 watch/reconcile 处理漂移。
  • 让客户端绕过 Proxy 直连 server 以“减少一跳”。

事实源：Deployment Modes、Workload Manager、MCPServer Reconciler。
